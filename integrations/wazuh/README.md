# LYSS → Wazuh

LYSS sends its scan results to Wazuh as JSON events: one per switch (level, pass / fail / unknown
counts), one per failed control, one per regression or fix, one per collection error, and the
number of unmanaged switches discovered. Wazuh turns them into alerts you can search, graph and
e-mail, next to your firewall and server logs.

| Rule | Level | When |
|---|---|---|
| 100801 | 3 | a switch was assessed: `LYSS: sw1 assessed, level 1, 4 failed control(s)` |
| 100810–100839 | 7 / 5 | a control fails, one rule per control: 7 for Level 1 (Baseline), 5 for Level 2 (Hardened) |
| 100840–100869 | 10 | **regression**, one rule per control: a control that passed now fails (configuration changed) |
| 100802 / 100804 | 5 / 10 | generic finding / regression (controls of a newer specification) |
| 100805 | 3 | a control that failed now passes |
| 100806 | 6 | a switch could not be collected |
| 100807 | 6 | unmanaged switches discovered on the network |
| 100808 | 3 | test event from Settings |

**Compliance.** The per-control rules carry the control's NIST SP 800-53 references as Wazuh groups
(`nist_800_53_CM.7`...), so LYSS findings appear in Wazuh's **NIST 800-53** compliance dashboard.
`lyss_rules.xml` is generated from the specification: `python tools/build_wazuh_rules.py`.

Fields: `lyss.event`, `lyss.device`, `lyss.host`, `lyss.site`, `lyss.control`, `lyss.control_level`,
`lyss.title`, `lyss.evidence` (first evidence line, already redacted), `lyss.iso27001`, `lyss.nist`,
`lyss.level`, `lyss.pass`, `lyss.fail`, `lyss.unknown`, `lyss.model`, `lyss.firmware`, `lyss.version`
(in alerts: `data.lyss.*`).

## 1. Install the decoder and rules on the Wazuh manager

```sh
sudo sh install.sh                          # copies lyss_decoders.xml + lyss_rules.xml, checks, restarts
sudo sh install.sh --regression-level 12    # same, with regressions at level 12 (to reach email_alert_level)
sudo sh install.sh --remove                 # uninstall
```

The script refuses to install if one of the rule ids (100800-100869) is already used, and restores
the previous state if Wazuh's configuration check fails.

## 2. Choose how events reach Wazuh

**A. Events file + Wazuh agent (recommended).** Works from any network, encrypted, buffered by the
agent. In LYSS: Settings → SIEM events → events file (e.g. `C:\LYSS\private\lyss-events.jsonl`).
Then make the agent of that machine read it, centrally, from the manager (agent group `lyss`):

```sh
sudo sh agent-group.sh <agent-id> 'C:\LYSS\private\lyss-events.jsonl'
```

or add the same `<localfile>` to the agent's own configuration:

```xml
<localfile>
  <log_format>json</log_format>
  <location>C:\LYSS\private\lyss-events.jsonl</location>
</localfile>
```

**B. Syslog.** In LYSS: syslog server = your Wazuh manager, port 514, UDP or TCP. Wazuh must accept
syslog from the LYSS machine's address (`<allowed-ips>` of the `<remote>` syslog block). Mind
machines with several interfaces (Wi-Fi, VPN): the source address is the one of the route to Wazuh.

## 3. Dashboard

Wazuh dashboard → Dashboard management → Saved objects → **Import** `lyss-dashboard.ndjson`
(overwrite). It adds **LYSS - Switch security**: level per switch, failed controls, failures by
switch, regressions over time, findings by NIST 800-53 control, collection errors. If a chart says
a field is missing, refresh the `wazuh-alerts-*` index pattern once LYSS events have arrived.
Generated by `python tools/build_wazuh_dashboard.py`.

## 4. Test

LYSS: Settings → SIEM events → **Send test event**, then in Wazuh look for rule 100808. On the
manager, without sending anything:

```sh
echo 'Nov  5 12:00:00 host lyss: {"lyss":{"event":"regression","device":"sw1","control":"LYSS-MGMT-001","title":"Telnet management access is disabled"}}' \
  | sudo /var/ossec/bin/wazuh-logtest
```

Expected: decoder `lyss`, rule 100840 (regression of LYSS-MGMT-001, NIST groups CM.7, SC.8, AC.17).

## 5. Switch logs: decoders included

`lyss_decoders.xml` also makes Wazuh understand switch messages it misses out of the box:

- **Cisco IOS with a time zone offset** (`972: Nov  5 19:42:37.960 UTC+1: %SYS-5-CONFIG_I: ...`,
  from `service timestamps log datetime msec localtime show-timezone` with a non-UTC zone). Wazuh's
  own `cisco-ios` decoders only accept a letters-only zone; the extra variants keep the same name,
  so Wazuh's Cisco IOS rules apply unchanged (4721: configuration changed).
- **Cisco Small Business / Business** (`%AAA-I-CONNECT: User CLI session for user ...`), with rules
  100870-100874: management session opened / closed, login refused, repeated refused logins
  (level 10, password guessing).

**Tested.** `bash test/run.sh` starts a disposable Wazuh manager (Docker), installs the decoder and
rules, and checks that every line of `test/samples.log` (fictitious data) fires the rule on the same
line of `test/expected.txt`. It also runs on GitHub whenever these files change.

## 6. Rescan on change

When Wazuh reports that a switch configuration changed (rule group `config_changed`, e.g. Cisco IOS
4721) or that an administrator session on a Cisco Business switch ended (`lyss_admin_session_end`,
rule 100872), LYSS rescans that switch at once instead of waiting for the next scheduled scan.

1. On the Wazuh indexer: `sudo sh reader-account.sh` creates the read-only account `lyss-reader`.
   It can only read those alerts (document-level security) and 5 of their fields (field-level
   security). The password is written to `/root/.lyss-reader.pw`.
2. In LYSS: Settings → Rescan on change → the Wazuh dashboard URL (`https://<wazuh>`), the account
   and its password, the interval (5 minutes) → **Test connection**.

LYSS only connects out to the dashboard (HTTPS); nothing connects to the LYSS machine. LYSS's own
SSH sessions are recognised and never trigger a rescan.

## Oxidized

`python -m lyss oxidized --url http://oxidized:8888 --events` assesses the configurations Oxidized
already backs up and sends the same events, without any SSH connection from LYSS. See
